Conventions used below (same as groups 1 to 5):
- "REF" = reference/catalogue data (same for every company). "CO" = per-company record (tenant data). "SIM" = simulated / demo-only behaviour.
- Workspace audit = `wsLog(action, target, cat)` (`lib/audit.ts:39-45`): appends `{seq, prev, hash, at, actor: getMe().name, action, target, cat}` to `WS_AUDIT`; in API mode it builds the entry but does not store it (`lib/audit.ts:43`). Platform audit = `adminLog(action, object, opts)` (`lib/adminAudit.ts:39-47`): appends to the **platform** Admin Console chain, no API-mode guard.
- **AI governance writes almost everything to the platform log.** `aiLog(action, name)` = `adminLog(action, name, { tenant: <role's tenant>, categories: ["AI governance"] })` (`features/ai/lib/ai.ts:78-79`). Only the two approval handlers and the shadow dismissal write the workspace log, with cat **`"AI governance"`** (`features/ai/services/ai.ts:45,53`, `features/ai/AiModule.tsx:40`). The module checklist claims the opposite (`docs/guides/checklist/ai.md`, Open question 1: "I log all of them to the workspace chain"). Assistant and API write the workspace log with cat **`"System"`**, custom tests with **`"Control"`**.
- "(svc)" = audit entry written inside the service function or approval handler; "(UI)" = written by the component after the service returns. A port that moves only the services loses every "(UI)" entry.
- Roles: base role = role id without trailing `2` (`lib/sod.ts:11`). Personas (`data/roles.json` ROLES): admin Jordan Avery, admin2 Casey Morgan, owner Owen Hart, owner2 Taylor Reed, analyst Sam Lee, auditor Morgan Blake, employee Priya Nair (tenant `cust-101`).
- Name matching: `isSamePerson` / `personKey` = first initial + surname (`lib/sod.ts:19-26`), so seed short names ("J. Avery") match personas ("Jordan Avery"). `runBlockReason` instead compares lower-cased full strings (`features/assistant/services/assistant.ts:167`), so "J. Avery" and "Jordan Avery" are different people there while `decideRun` (via `assertNotSelf`, `:175`) treats them as the same.
- Error contract: services throw `SodError` (role and SoD rules) or return `{ ok: false, msg }` (AI) / `null` (Assistant, API: "not found"). UI wraps calls in `attempt` (`components/kit/sodKit.tsx:14-19`): SodError text as a toast, anything else `FAIL_MSG` "Something went wrong. Please try again." (`lib/grcSod.ts:8,11`).
- `viaApi(mock, real)` (`services/http.ts:19-21`). **All group 6 API stubs use paths without the `/ws` prefix** (`/ai/...`, `/assistant/...`, `/api-keys`, `/webhooks`, `/custom-tests`, `/api-events/test`). - **The production AI features have no demonstration to preserve**: no model call, no opt-in, no PII blocker or masking, no per-record context (section 4). They are new scope inside group 6; the inventory can only fix what surrounds them (who may ask, audit, drafts labelled for review).
- **AI governance audit goes to the platform log** (`aiLog`), contradicting its own checklist; the three workspace entries use a category with no tab; `ai.shadow.dismissed` is written twice, once without tenant; registering from a shadow entry removes it silently.
- **Role mismatches**: analyst may register AI by rule but cannot open the module; owner is an assistant approver and may manage agents by rule but cannot open the module, which makes service-account raises and recertifications impossible in the UI; the "system owner by name" manage path is unreachable.
- **AI inventory tab "Active" matches no system**; the "Impact assessments approved" counter can exceed its denominator; lifecycle never changes; edits allowed on Archived systems; "Start review" silently un-archives.
- **EU classification**: a draft changes the visible class at once and overwrites a confirmed one; confirming sets the guardrail without the guardrail four-eyes; "Complete review" approves a system whatever its classification, FRIA or bias state; the risk tier can only change through classification (`setTier` dead code).
- **Impact assessment**: submit without recording; approve forces status Complete; return allows the author while the UI does not; "evidence D-07" and ISO 42001 clause credit are fiction.
- **Signals**: seed-only, index-addressed, dismiss without reason; risks/issues created without `risk.created`/`issue.created`, static "Due 14d", owner by short name.
- **Assistant**: Ask has no service role check; prompt text in the audit log; one thread per browser shared across personas; canned replies state unsupported facts; "Mark reviewed" marks nothing; agents do nothing real; MCP grants are not tied to agents; delete strands approvals; expired enable requests leave an agent permanently "Pending approval"; transition period restarts on reload; lapse sweep is browser-driven.
- **API**: unrevealed approved keys stay Active forever once the 60-minute button disappears; no key expiry or rotation; service accepts any label; no webhook signing secret despite the "generated automatically" copy; webhook with no events silently gets `control.failed`; no delivery log; Paused webhooks can be tested; pending webhooks deletable; deletes without confirmation; event-stream row keys can collide.
- **Approvals**: expiry never runs `closed`; group 6 kinds are not in `SERVER_KINDS`/`SERVER_ROUTES`, so the production `decide` would call a non-existent `/approvals/:id/:decision`.
- **Not linked**: the Assistant and its agents are not in the AI register (ISO 42001 inventory); AI-05/AI-06 rows are free text; vendor `ai` flag unused; custom tests unrelated to controls and tests (overlap with group 1 tests and group 7 integrations).
- Checklist drift: `docs/guides/checklist/ai.md` (aiLog to workspace; Rivera surname rule; super can confirm), `assistant.md` (super/admin/owner manage; "Run now" on Paused), `api.md` (super/owner manage; "then the key is revoked" after 60 min, not true without a reveal attempt).
