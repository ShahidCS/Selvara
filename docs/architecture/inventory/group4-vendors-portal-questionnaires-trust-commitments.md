### 0.5 Approvals engine use in this group (`lib/approvals.ts`, `lib/rules.ts`, `lib/approvalKit.ts`)
Engine rules as in groups 1-3: approve needs reason >= 10 (`REASON_MIN`, `lib/rules.ts:7,44`); `decideApproval` also requires 10 for reject (`lib/approvalKit.ts:67`); requester never decides, `forbid` people never decide, repeat voters refused, wrong role refused, expired refused (`lib/rules.ts:29-37`); only the requester withdraws (`:39-43`); a 2-approver request records the first vote as `approval.<kind>.approval.recorded` and stays Pending (`lib/approvals.ts:50-52`); the handler `apply` runs once on the final approval, then `<kind>.applied` is logged cat Approval (`lib/approvalKit.ts:74-83`); `closed` runs on reject and withdraw only (`:65,69`), **never on expiry**. ### 1.4 Computed values
- Tier cards: count per tier and count with `/Overdue/` due (`VendorsModule.tsx:60-64`).
- Review-due sort: "Overdue Nd" -> `-N`, a parseable date -> its time, anything else (for example "Due in 12 months") last (`:53`).
- Open findings = findings with status != Closed (`VendorDetail.tsx:37`).
- `vendorDue` (Overview) and bell alerts: overdue text or status In review (0.6, 0.7).
- Next review: never a date; reassessment and tier change write the window text, which no code parses, so a reassessed vendor can never become overdue again.

### 1.5 Cross-module links
- IN: My Work vendor requests (0.8). OUT: Overview KPI/Needs attention, board pack, bell, Team rule, server Reports CSV (0.7).
- "Send questionnaire" is **not** linked to the Questionnaires module, the in-shell vendor view or the standalone vendor portal; nothing comes back from a vendor (2.4).
- No link to Risk (third-party risks are a separate register category "Third party", group 3) or to Contracts/Commitments.

### 1.6 Simulated
- `vInit` fabricates, for every vendor that lacks them (seed, created, onboarded): certificates (Critical: SOC 2 Type II valid to "30 Jun 2027" and ISO 27001 valid to "14 Mar 2027"; Medium: ISO 27001 "Expiring" "20 Nov 2026"; Low: none), a finding when score < 75 (Critical "No recent independent pen-test on file", others "DPA not countersigned"; High when score < 65, id `VF-` + 3 letters of the vendor id), monitoring signals for Critical ("TLS certificate renewed", "New sub-processor disclosed"), discovered applications (non-Low "<name> connector" 12 users sanctioned; Low "<name> (shadow)" 3 users unsanctioned) and the gate (`lib/vendors.ts:36-41`). **A newly added or onboarded Critical vendor therefore shows two "Valid" certificates nobody provided**, and an onboarded vendor (score 70) shows a fabricated finding.
- DPA "On file"/"Missing" is derived from the tier (`VendorDetail.tsx:55`).
- Monitoring, discovered applications and the "Overdue Nd" texts are static; "Send questionnaire" sends nothing.

## 8. Gaps and oddities found (decide before porting)
- **Almost every audit entry is written by the UI, not the service** (all vendor, questionnaire, trust and commitments actions except the approval handlers and `trust.access.approve.denied`). A port that moves only the services loses them. Questionnaire "Export responses", trust "Accept NDA"/"View", vendor portal views and DataTable "Export selected" write nothing.
- **Questionnaire four-eyes bypass**: "Answer next 10" reaches Complete (= sent) with no `q.send` review (`questionnaires.ts:76`); `requestSend` then refuses "already been sent".
- **Vendor portal submit ignores readiness**: the standalone portal's Submit button is `aria-disabled` only and calls submit regardless (`Questionnaire.tsx:39`); the service does not check either. The clarification button does check.
- **Seed vendor deep links and bell links break** before the register renders (ids assigned lazily; `/ws/vendors/undefined` in the bell; Team rule ids undefined).
- **Fabricated vendor evidence**: `vInit` gives new Critical vendors two "Valid" certificates and others findings, monitoring and apps nobody recorded; DPA derived from tier.
- Three disconnected vendor-questionnaire paths: Vendors "Send questionnaire" (status flip only), the in-shell vendor role view (5 free-text questions, global answers, "ACME Ltd", editable after submit) and the standalone `/vendor-portal` (12 structured questions, "Example Co", no server routes). None writes to the vendor record.
- Trust access approval SoD is a dead check (name vs email; `enteredBy` never set); approval re-activates revoked accounts and records "NDA Signed <today>" without any NDA; one admin can unblock a domain and approve its request.
- Trust public side: personal data (emails) written into audit targets (`trust.subscribed`, `trust.access.requested/ignored`, `trust.access.approved/denied`); question logged before the call; the "public" page requires a signed-in persona; questions have no rate limit; replies promise a hand-off and notices that never happen.
- `trust.publish` new-mode duplicate check never fires; resource names are not unique while handlers and the duplicate check look up by name. The Trust resource button tests `!!t.publishPending`, which stays set after expiry (no `closed` on expiry), so it can stay "Awaiting approval" for good. No group 4 module calls `sweepExpired`; `stillPending` ignores `expiresAt`.
- Vendor request ids repeat after a dismissal in the demo (`VR-` + length + 4); the server uses a counter. The demo deletes decided requests; the server keeps a status. The requester is never told.
- Vendor non-Critical request approval and gate approval leave no approval record (single person); gate approve has no state check; block and finding close need no reason; reassessment and certificates need no second person; waiver expiry and certificate expiry are never enforced; "Approved with conditions" records no conditions; due dates become text that never goes overdue again.
- Vendor `data` flag stored as `v.ai` and never shown; adding a vendor with an existing name navigates to the older record (`VendorForms.tsx:45`).
- Answer library: verify is single-person with no engine record; `editedBy` never written; no edit/unverify/delete; `uses` static; verify logs even when already verified. Import/total/due validation lives only in the UI; due is free text.
- Index addressing across stubs (questionnaires, answer library, trust accounts and resources, request access, vendor findings) and API stub paths without the `/ws` prefix used by the group 1-3 server.
- Commitments: incident is one global flag with no tenant, no stored summary, no deadline and no close outcome; starting/closing has no second person; the platform admin log gets an entry with an empty tenant and, unlike `wsLog`, also in API mode; "Run contract analysis" has no role check and logs a run that did nothing; "Import & analyse" analyses nothing; table rows keyed by (non-unique) name. The commitments checklist still says adminLog is not ported (`docs/guides/checklist/commitments.md:11,17`), but it is.
- Matrix differences in section 7 (analyst in the vendor row, no rows for incidents or the vendor portal, stale persona names).
- Hex literal `#fff` on the public Trust header (`TrustPublic.tsx:39`, design-token rule). Plain `Table` instead of `DataTable` for vendor requests, vendor record tables, Trust tables and standard terms; Vendors uses older `KpiCard` tiles (kit convention).
- Checklist drift: `docs/guides/checklist/questionnaires.md:26` still says Verify has no role gate (it now has one); `docs/guides/checklist/vendorportal.md:45` says the in-shell set has 6 questions (seed has 5).
