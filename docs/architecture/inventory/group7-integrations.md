- **Outbound calls only from the server** (Vercel API routes), never from the browser (CSP `connect-src` stays as it is). Provider hosts are fixed per provider, except the Okta organisation domain, which a company admin types and must be validated (Okta domain pattern, then the same resolve-and-refuse-private-addresses check as webhooks, `server/ws/webhooks.ts:48-75`).
- **Two credential layers.** (a) Platform credentials that Selvara's owner creates once in the provider (an app registration or a principal) and stores as **Vercel environment variables** (`server/env.ts:14-17` reads config there; it is the pattern of `ANTHROPIC_API_KEY`, `server/claude.ts:1-5`). (b) Per-company identifiers and, only where unavoidable, per-company secrets, which a **company admin** creates in the company's own provider console and enters once; secrets are sealed with AES-256-GCM under `SERVER_SECRET` (as webhook signing secrets are, `server/ws/webhooks.ts:33-45`), never returned by any data route, never written to the audit log, never shown again; identifiers (installation id, role ARN, tenant id) are stored in the company's `ws_records`. Short-lived access tokens are minted per sync and kept in memory only. Note: sealing derives its key from `SERVER_SECRET`, so rotating that variable makes every sealed connector secret unreadable (same for webhooks): a rotation procedure is needed.
- **Prefer no shared secret at all:** GitHub App installation (customer grants, Selvara holds the key), AWS role assumption with an external id, Entra multi-tenant app with admin consent, Okta service app with a public key Selvara gives, Google domain-wide delegation to Selvara's service account. In each of these the customer creates no password that leaves its tenant.
- The permission lists below are the minimum for the demonstration's features (section 3) and are **to be verified against each provider's current documentation** before use (this inventory was written without network access to provider docs).

## 7. Gaps and oddities found (decide before porting)
- **Nothing is connected to anything.** Connector status is read by no other module; tests, people, access, vendors and AI keep their seed data whatever is connected. TST-06 shows a fresh "Fail" from Quartz, which is Not connected; TST-01 passes using Arbor Identity, Meridian and Ironwood data that no sync produced; "Create Tasklane ticket" works while Tasklane is Not connected.
- **Sync heals**: syncing marks a Degraded connector Healthy with no cause or check; the service also marks a disconnected connector Healthy (UI hides it); "Sync all" is audited as "all connectors" even with none connected.
- **Copy that is not true**: "Connectors are read-only and scoped to the least privilege needed" and KPI "Read-only / Least privilege" next to Tasklane's "Read/write remediation issues" offered as "Connect read-only"; "Data is pulled read-only to evaluate controls and tests"; KPI "Last sync 4m ago" literal with caption "Identity source"; "syncing…" forever; "1,284 users" against 10 people. Checklist open question 4 says the "does not write back" copy was anonymised to "Assurance": the page now says "Selvara" (drift).
- **One toggle endpoint** for connect and disconnect: a repeated or retried request reverses the state; production needs separate commands.
- **Keyed by display name** in the route, the table and the audit target; no stable id.
- **Disconnect on the connector page** navigates away before the result arrives, so a refusal toast appears on the list page.
- **No confirmation, reason or second person** for connect or disconnect; no record of who connected a connector or when.
- **Audit**: everything "(UI)"; disconnect duplicated into the platform log with tenant; `ropaFor` maps the entries to PA-15, not PA-14; export not audited.
- **Stubs** bypass `wsPost` and the `/ws` prefix; `INTEGRATIONS` seed not emptied in API mode.
- **Two ingestion paths** will exist: connector results and the group 6 push API (`/api/v1/events` feeding custom tests). The seed's custom tests T1/T2 ("Meridian") duplicate checks an AWS connector would run; decide which path owns which check.
- **Names reused across modules without links**: Tasklane, Ironwood, Northlight are both connectors and MCP servers (Tasklane MCP "Granted" with write while the connector is Not connected); Arbor Identity, Meridian Cloud, Northlight, SecureAware are connectors, vendors and Trust sub-processors.
- **Uncovered connectors** in the owner's list: device posture (TST-03 "MDM", People devices), training (SecureAware, My Work t5), ticketing (Tasklane), vulnerability scanning beyond GitHub alerts (Quartz) and monitoring beyond AWS (Northlight) stay simulated or empty in production.
- **Checklist drift** (`docs/guides/checklist/integrations.md`): table rows still describe the drawer and the old role list (super, admin, owner, analyst) as "Done"; the Wave E note and the Hardening section supersede them; open question 5 (drawer) is obsolete.
