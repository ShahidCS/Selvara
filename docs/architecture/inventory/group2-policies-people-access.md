### 0.5 Approvals engine and the "approval flow" layer
- Engine (`lib/approvals.ts`, rules `lib/rules.ts`): record `{id, kind, title, subject, requestedBy, requestedByRole, payload, needs, approverRoles, forbid, approvals[{by,at,reason}], status Pending|Approved|Rejected|Withdrawn|Expired, createdAt, expiresAt, decidedReason?, ticket?, domain}` (`:11-18`). `requestApproval` audits `approval.<kind>.requested` (`:23-34`); `approvalBlock` (`lib/rules.ts:29-37`) refuses non-Pending, expired, wrong base role, requester, forbidden person, repeat voter; `approve` needs reason >= 10 (`REASON_MIN`, `lib/rules.ts:7,44`), stores 300 chars, audits `approved` or `approval.recorded` (`:46-54`); `reject` does not check reason length (`:55-60`); `withdraw` requester only, Pending only (`:62-67`); `sweepExpired` -> Expired + `approval.<kind>.expired` (`:36-40`).
- Approval flow (`lib/approvalFlow.ts`) used by People and Access: modules `registerKind(kind, {describe, apply, closed})` (`:25`); `settle()` sweeps expiry then runs `apply` once for Approved and `closed` once for Rejected/Withdrawn/Expired (`:30-40`). `settle` is only called by the services before an action and by `PendingApprovals` every 30 s while mounted (`features/mfa/PendingApprovals.tsx:28`). The `settled` set is session memory, so the "once" guarantee is per browser session.
- `whyCannotDecide(a)` (`lib/approvalFlow.ts:44-53`): engine block; admin-domain needs elevation; if `payload.approver` (named approver) is set and the actor does not act as them: refused when `needs < 2` or the actor already voted ("Only the named approver (<name>) can decide this request.").
- `decideApproval(id, ok, reason)` (`:56-78`): reason >= 10 for approve and reject; for `needs >= 2` the final approval must include the named approver or their delegate ("The named approver (<name>) must also approve this request."); records `payload.delegated[me] = named` and audits `approval.<kind>.on_behalf` "<title> (<id>): approved|rejected by <me> on behalf of <named> (delegation)" when acting by delegation; then `settle()`.
- `withdrawApproval` (`:79-83`) -> engine withdraw + settle.
- **Effects run from whoever's action triggers `settle()`**: an expiry noticed during someone else's action is audited with that person as `actor` (`wsLog` uses `getMe()`).

### 1.3 User actions
Reason helpers (null = allowed; services call `guard()` with the same function, `policies.ts:82-126`):
- `whyCannotEdit` (`:84-89`): role admin/owner ("Not permitted: editing a policy requires admin or owner."); actor is owner ("Only the policy owner (<owner>) can edit content. An admin can reassign ownership."); working version, if any, is Draft ("Content is locked while the version is <in review|approved>.").
- `whyCannotSubmit` (`:90-95`): working version exists ("There is no draft to submit.") and is Draft ("The version is already <status>."); role admin/owner; owner only ("Only the policy owner (<owner>) can submit it.").
- `whyCannotApprove` (`:97-104`): working version In review ("Only a version in review can be approved."); role admin/owner; approver named ("No approver has been named yet."); actor not author/lastEditor/any editor ("Segregation of duties: the author or a last editor cannot approve their own policy."); actor `actsAs(approver)` ("Only the named approver (<name>) can do this.").

## 4. Server checklist distilled (rules a server must reproduce)
1. Module visibility per ROLE_MODS (0.1) and SERVER_READY; employee reads policies, acknowledges, and requests access; auditor reads policies (and today can also acknowledge from the record page).
2. Identity by user id: owner, author, editors, lastEditor, named approver, delegate, requester, beneficiary, subject, review creator, account holder. Never by display name or initial-based matching.
3. Policy versioning: one live (Published) and at most one working (Draft/In review/Approved) version; minor bump on a new draft from live; 0.x -> 1.0 at first approval/emergency; Approved and Published versions immutable; superseded versions kept with `supersededAt`; server-owned version numbers and timestamps; append-only change log with (date, version, who, what, why).
4. Policy edit/submit: base admin/owner AND the policy owner; content locked unless Draft; new draft from live requires reason >= 10; name required <= 160, body <= 8000, cycle in {6,12,24}.
5. Named approver: admin/owner member, not author/lastEditor/editor; changeable only while In review by the owner; (decide: also exclude the owner/submitter, see gaps).
6. Approve: named approver or live delegate, admin/owner, not author/editor; reason >= 10; effective date today..today+90; Publish: same people rule, effective date reached; sets next review = effective + cycle; resets acknowledgements for the new version.
7. Request changes (approver or delegate, not author/editor) and withdraw (owner) need reason >= 10 and clear the approver.
8. Emergency publish: base admin; Draft or In review only; justification >= 20; publishes at once; exception record with due date = 5 business days (server calendar); engine approval `policy.emergency` approverRoles admin/owner, forbid publisher + version authors/editors; retrospective approve/reject reason >= 10; late decisions flagged; decide what rejection does to the published version.
9. Reassign owner: base admin, successor admin/owner member, reason >= 10, not self, not current owner, not the named approver of an In-review version.
10. Map control: admin/owner, control must exist, idempotent. Remind: admin/owner, rate-limited, real recipients.
11. Acknowledgement: authenticated user + policy id + exact live version + server timestamp; only for published policies; one per user per version; maintain acceptance counts from real acknowledgements and real workforce size.
12. Delegation: admin/owner to another admin/owner, 1..14 days, reason >= 10, one live per delegator, no loops, no chains, not for platform approvals, not when the delegator raised or is the subject, delegate keeps own exclusions and counts only as the named approver; end by delegator or any admin; expiry job; audit on-behalf decisions.
13. Member MFA reset: requester base admin; not self; subject has MFA; one pending per subject; three identity checks, reason enum + text >= 10, ticket regex, named approver from eligible people; approvals needs 2 if privileged else 1; named approver (or delegate) must be among approvers; 24 h TTL; requester withdraws; effects only on final approval (revoke sessions, remove factors, force re-enrolment, invalidate recovery codes, notify); add step-up auth (matrix) server-side.
14. Offboarding: admin/owner; not self; transfer target must be another member; last Company Admin protected (also re-checked at apply); privileged subjects need a second admin/owner (72 h, one pending per subject); on completion revoke every grant, deny pending access requests, (decide) transfer owned records and end sessions/delegations atomically.
15. Contractor creation: admin/owner; validate name/role/dept server-side; unique ids; audit in the server.
16. Access request: anyone with access or work module; employees only for themselves; level enum; Admin level reason >= 10; system <= 100, reason <= 300.
17. Access decision: admin/owner, not requester, not beneficiary, reason >= 10; privileged (level or system) needs a second, different admin/owner (72 h); grant only on final approval; de-duplicate grants.
18. Access reviews: admin/owner create (snapshot of grants, immutable scope); decisions by admin/owner not the account holder; complete only when all decided; privileged reviews completed by someone other than the creator; revocations applied on completion with follow-up for unmatched rows; idempotent completion.
19. Expiry jobs: `policy.emergency` overdue marking, approvals TTL (24 h MFA, 72 h offboard and access second stage), delegation expiry; attribute system-initiated audit entries to the system, not to whoever triggers the sweep.

## 5. Gaps and oddities found (decide before porting)
- **Policy text is never shown to readers**: record page, register and My workspace have no body display, yet employees "Read & acknowledge".
- **Acknowledgements do not move the acceptance ring**: `acceptance.done` is random/zero and never incremented; Remind reports a fictitious number.
- **Owner can approve their own submission** when they are not in the version's editor list (e.g. after reassignment, or on migrated seed policies whose author is the previous owner): Submit only excludes author/editors, not the owner/submitter. The checklist claims "owner = approver is refused".
- `setApprover` exists (`policies.ts:183-194`) but no UI calls it; seed P-006 and P-011 are In review with no named approver and no way to name one except withdraw + resubmit. Their owners (P. Nair = employee persona, A. Rivera = no persona) cannot act until an admin reassigns ownership; P-003/P-012/P-014 (A. Rivera, N. Kim) are likewise frozen.
- Emergency publish on a 0.x draft records the exception and approval payload with the **old** version (`ver` captured before the 0.x -> 1.0 bump, `policies.ts:256-258`): banner says "v0.1", and `whyCannotDecideException` cannot find the version (`:121`), so its author exclusion falls back to the engine's forbid list.
- Rejecting an emergency change leaves the emergency version Published; overdue exceptions have no escalation; the engine TTL is 365 days.
- Emergency publish is allowed to any admin, not only the owner, and bypasses the owner-only edit rule; whether that is intended needs a decision.
- No path back from Approved (cannot return an approved-but-unpublished version to draft or cancel it); future effective dates need someone to press Publish later (no scheduled publish).
- No "reviewed, no change" action: a Review-due policy can only be cleared by publishing a new version. KPI caption says "past the review date" but counts anything within 30 days.
