# Inventory 04: Admin Console and app shell (GROUPCODE AD)

Phase 1 front-end inventory, documentation only. Scope: features `customers`, `billing`, `rates`, `mfa`, `adminlog`, `elevation`, `platformsecurity` (all under `/admin/*`), plus the cross-cutting shell (`front-end/src/components/shell`) and kit (`front-end/src/components/kit`, including `kit/admin`). Field names and types only; no seed values are copied.

Conventions used below:
- "Demo" = the default build (`API_ON` false): synthetic in-browser data, rules in `src/services` / `src/features/*/services`. "API" = `NEXT_PUBLIC_API_MODE=http`: every Admin Console module renders a separate `Api*` component that talks to the server (`front-end/src/server/admin.ts`, `admin8.ts`, `support.ts`, `helpdesk.ts`). The two variants of a module are listed as separate screens because they use different entities.
- Roles: `super` (and `super2`, a second demo persona of the same role) = Platform Super Admin; `support` = Platform Support. From `src/data/roles.json` ROLE_MODS: `super`: `admin: *`; `support`: `admin: customers, billing, rates, mfa, adminlog, security` (not `elevation`). No company role can open `/admin/*`.
- "Elevated" = a live platform elevation (server: `elevations` row with `tenant_id` null; demo: browser state in `src/lib/elevation.ts`).
- Timestamps on the server are epoch milliseconds (`bigint`). Money on the server is integer minor units.

### Gaps and observations

1. Demo and production are different products for Customers & Usage. The demo has plans, module entitlements, usage metering (screenings, identity verifications, storage, API calls), seat limits, onboarding with region / currency / billing method, and full tenant user management by platform staff. Production has only companies (code, name, status, counts), create / suspend / reactivate, the first-admin link and support access. None of the demo items has a server model. The screening / IDV usage metrics look inherited from an earlier KYC product and may not belong in a GRC plan model. The redesign must decide whether Plan limits, Module entitlement and Usage are real entities.
2. Platform staff editing tenant users (S-AD-04) conflicts with the production rule that the platform never writes company rows (0007 restrictive policies). Recommend dropping it or routing it through the support-session model with a write grant (no such grant exists today).
3. `tenants.region` and `tenants.plan` exist in 0003 but no production screen reads or writes them. The plan now lives in `billing-account` (`platform_records`). Data residency (region locked at creation) is shown in the demo only. This matters for schema-per-tenant placement.
4. Billing, rates and price list are generic JSON records in `platform_records` (kinds `billing-account`, `billing-invoice`, `billing-entry`, `billing-plan-request`, `billing-plan-answer`, `billing-price`, `billing-checkout`, `billing-provider-event`, `billing-rate`, `billing-rate-refresh`). They are candidates for typed control-plane tables: Subscription (= billing account), Invoice, InvoiceLine, LedgerEntry, Plan / PriceList (versioned), PlanChangeRequest, ExchangeRate, TaxRule, ProviderEvent.
5. Demo fallback endpoints that do not exist on the server (dead code paths): `/customers...`, `/billing/...`, `/billing/approvals/:id`, `/rates/...`, `/rates/approvals/:id`, `/admin/audit/exports`, `/admin/audit/ropa/exports`, `/admin/audit/verify`, `/admin/audit/packages`, `/notification-preferences`, `/approvals/:id/:decision`. Production screens use the `Api*` components instead.
6. Server endpoints with no Admin Console screen: `POST billing/stripe/webhook` (system only, expected). All `admin/*` routes have a screen.
7. Rule differences between demo and server: demo price-list change is single-person (server four-eyes); demo "reject held rate" is four-eyes (server single-person); demo void has no threshold (server: void above the threshold is four-eyes); demo MFA reasons differ from the server's four reasons.
8. Platform audit log in production lacks fields the demo shows: lawful basis, data categories, before / after, role, tenant filter, RoPA activity link, exports and evidence packages. `audit_log.basis` exists (0003) but the platform screen does not show it. RoPA (ProcessingActivity) exists only as demo seed data, with no server table.
9. Notifications: the bell is hidden in API mode. Server `notices` are written (MFA approver, MFA subject, support answer, account security) but in production they are shown only through `GET me/security` on the account page, not in a bell. Read state and preferences are browser-only, and preferences are keyed by role, not by person. The admin-space bell items (pending MFA resets, past-due customers) read demo data only. A Notification entity with per-person read state and channel preferences is needed.
10. The approvals pill exists only in the ws space. Platform staff have no cross-module "waiting for you" count. Platform requests are spread over Customers, Billing, Rates and MFA "Requests" tabs, all fed by one endpoint (`GET admin/approvals`) and filtered client-side.
11. The command palette searches module names only. There is no record search, so no search index is needed for this group.
12. Step-up re-authentication is not required for any Admin Console action (elevation plays that role). The demo shows a simulated hardware-key step at elevation. Production elevation has no second-factor check beyond the signed-in session; the security rules page claims a hardware key and a network allow-list, which are not enforced in code reviewed here.
13. Sign-in blocks are kept in `kv` (namespaces `ip`, `ipblocks`). IP addresses are personal data. Retention follows the kv expiry (30 days after a lift). They are not typed tables.
14. Personal or sensitive data in this group: platform staff and company admin names and emails; billing contact name, email and address; IP addresses in audit entries and blocks; MFA reset details (identity-check free text, reason) about a named person; support question bodies (free text; staff are told not to ask for passwords or customer data, but nothing enforces it); support-session views expose company member names and emails to platform staff. No special-category data was found.
15. Support grant creation and revocation (company side, `team/support`) belong to another group but are required for S-AD-08. A grant is not an AccessRequest in the GRC sense. Elevations and grants together are the platform's privileged-access records.
16. Brief entity coverage for this group:
    - Covered: Tenant (E-AD-01), Plan (E-AD-21; demo E-AD-03), Subscription (as billing account E-AD-17), Invoice (E-AD-18, with ledger E-AD-19), AuditLogEntry (platform scope E-AD-29).
    - Partially covered:
      - User: platform staff E-AD-08; demo tenant users E-AD-07.
      - Membership: counts, support view, switcher.
      - Role: platform roles super / support; company roles shown read-only.
      - Permission: static ROLE_MODS, no server entity.
      - Notification: E-AD-38..E-AD-40.
      - ProcessingActivity (RoPA): demo only, E-AD-32.
      - AccessRequest: support grant and elevation are platform access records, not GRC access requests.
    - Lacking (other groups): Framework, Requirement, Control, ControlMapping, Evidence, Policy, Asset, Threat, Vulnerability, Risk, RiskTreatment, Vendor, Questionnaire, Assessment, Audit, Finding, CorrectiveAction, TrustCenterPage, DPIA, DataSubjectRequest.
17. Undetermined: the full company-side billing screen (`ws/billingws`) and Help centre asker screens are in other groups. Whether `tenants.status = 'Closed'` has any path (no UI or function sets it). Whether `profiles.status` (Pending, Rejected) is still used now that roles come from memberships.
