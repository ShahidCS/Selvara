## Risk, people and third parties (RK)

Phase 1 front-end inventory, group RK. Features: `risk` (with `import`, scoring criteria, governance, interested parties), `people`, `access`, `ai`, `vendors`, `vendorportal`, `questionnaires`, `trust`, `trustpublic`, `commitments`.
Sources read: `front-end/src/features/<name>/`, `front-end/src/server/ws/{risk,people,access,flow,ai,vendors,questionnaires,trust,commitments,foureyes,common,store,routes}.ts`, `front-end/src/server/{vendorportal,trustpublic,visitor}.ts`, `front-end/src/lib/{risk,riskBoard,rulesWs}.ts`, `front-end/src/data/{roles,nav,riskRef,vendorQuestions}.json`.

Conventions used below:
- Endpoints are the route keys as registered (`"<METHOD> <path>"`), served under the API base. `ws/...` routes run through `wsRoute` (signed-in member of the session's company, role gate from `ROLE_MODS`, one transaction with RLS, audit entry in the same unit of work).
- "ws_records `x`" means a row in the generic `ws_records` table with `kind = 'x'` (JSONB `data`, `version` for optimistic locking, soft delete via `deleted_ms`).
- Role names are the base company roles from `data/roles.json` (`admin` has every workspace module; `super`/`support` are platform roles and never open these modules on the server).
- Module access from `ROLE_MODS.ws`: `risk` = admin, owner, analyst; `people` = admin, owner; `access` = admin, owner, employee; `ai` = admin, owner; `vendors` = admin, owner; `questionnaires` = admin, owner, employee, vendor; `trust` = admin, owner, vendor, viewer; `commitments` = admin, owner.

### Gaps and observations

1. ISO/IEC 27005 asset-based concepts are absent. There is no Asset, Threat or Vulnerability entity, field or screen anywhere in this group (the only trace is the register search placeholder "ID, title, threat, team"). A risk is a free-text scenario (title, desc) with a category. The redesign must add Asset, Threat and Vulnerability tables and a risk-to-asset/threat/vulnerability link, or record that the event-based approach of ISO 27005:2022 is the chosen method.
2. Risk treatment is not its own entity. `treat` is an enum on the risk, and treatment actions are an array inside the risk record. The API addresses them by array index (`/actions/:n`), and they have no ids, no status history and no evidence link. A RiskTreatment table (plan, option, owner, due, status, linked controls) with child actions is needed. Risk acceptance (including Board evidence) is also embedded, with three slots (`acceptance`, `pendingAcceptance`, `invalidatedAcceptance`). It should become an acceptance table with history. Board minutes are stored as a file name only, and no file is kept.
3. The risk criteria are code constants: scales, bands, appetite (11), Board threshold (15), the acceptance ladder, category-to-team map and jurisdictions. They are not per-tenant. On the server, `jur` is always "Global" and `register` is always "Information Security", so there is a single register per tenant. Enterprise risks (E-RK-09) and the register owner exist only in the demo.
4. Reads write. `GET ws/data/risk` (and the vendors, AI, trust, access and people data routes) sweep approvals and record expiries (acceptance expiry, staged import cleanup, expired requests) inside the GET transaction, retrying on conflict. The redesign should move these sweeps to scheduled jobs.
5. Server endpoints with no screen: `POST ws/answer-library/:id` (edit answer); `ai-shadow` records (there is no server writer, so discovered AI is always empty); `GET ws/data/people-approvals` is used only through the shared approvals panel. Screens with no working endpoint: the AI "Risk-classify" modal (`setTier`) is refused in both modes; S-RK-32 (demo vendor portal with an MFA step) and S-RK-09/S-RK-10 enterprise risks have no server equivalent.
6. Demo-only behaviour: device posture values, vendor monitoring and applications, grant statuses other than Active, the demo incident clock, static contract analysis, the client-side attempt counters of the demo portal, analyst registering AI systems, and name-based SoD checks (`sodReason`, `isSamePerson`, compared by display name; the server compares user ids).
7. The inbound questionnaire (E-RK-33) has no question or answer rows. "Advance" adds 10 to a counter, and the import stores only a question count. There is no link to the answer library, and `uses` is never incremented on the server. A Question/Answer model is needed if the product is meant to answer real questionnaires. KB documents and interested parties have no delete endpoint.
8. There are two vendor questionnaire variants and two catalogues: the member variant uses `trustSeed.json` `VENDOR_Q` with index-aligned `answers[]`, and the portal variant uses `vendorQuestions.json` (12 questions with ids, critical flag and evidence). Both live in one kind (`vendor-questionnaire`). The redesign should use one Questionnaire template / Assessment / Response model with versioned submissions (the portal already has `version`, `history`, `base`).
9. Vendor findings (E-RK-26) are separate from audit Findings and Issues. Certificates are not Evidence records. Portal evidence files are not Evidence records either: they sit under `vendor-q/` storage and are not malware-scanned. The vendor logo is a data URL stored inside the vendor record. The `data` boolean (processes customer data) alone drives the public sub-processor list, and region is always "—".
10. Identity and naming: most records store display names next to ids (owner, by, requester, editors, `nda` text "Accepted <date> by <name>"). Trust accounts reference documents by NAME (`access[]`) and viewers by email, so a rename silently changes access. Trust subscriptions use two key shapes in one kind (user id vs email hash).
11. Personal data: contractor names; member MFA status; MFA-reset payload (identity-check confirmations, ticket, free-text reason); access grants per person; vendor contact emails (portal); Trust Center requester emails, account viewer emails, subscriber emails, chat questions (free text from anonymous visitors, may contain PD); OTP session emails in kv; audit targets that embed names and masked emails. AI signals come from the PII blocker and may describe personal data; AI `dataReached` and FRIA summaries may describe special-category processing. Incident summaries and outcomes may describe breaches of personal data. Retention rules are needed for all of these (see `SOD_MATRIX.md` section 14, draft).
12. Vendor actors. A vendor contact is either (a) a member of the customer tenant with role `vendor` (sees only `questionnaires` (own assigned ones) and `trust` (public view); `ws/members` returns empty) or (b) an anonymous verified visitor of the portal. Option (a) makes vendor staff tenant members, and the redesign must decide whether that stays (Membership with an external flag) or moves to the visitor model.
13. What anonymous Trust Center visitors can see: company name; verified library answers (FAQ); sub-processor names and purposes; the last 5 public publications; control status per control domain (Pass / In review, computed live from Control records); the full document list, including names of NDA-gated documents and whether each has a file. A verified visitor also sees their masked email, their company's account (NDA state, document names granted), their own requests and their subscription. Anonymous visitors can open public documents (60 s signed link), ask the chatbot (answers only from verified answers), and unsubscribe by token. Verified visitors can also request documents, accept the NDA for the whole domain's account, and subscribe. Any one verified address on a domain accepts the NDA on behalf of every viewer of that domain account. All visitor actions are audited as "Visitor <masked>" or "Public visitor" with a null actor id.
14. What a vendor portal visitor can see and do: customer company name, vendor name, due date, status, version, clarification note and reopened question ids, the 12 questions, their own answers, comments and file names, and readiness counts. They can save drafts, upload one file per question, submit and sign out. Nothing from other questionnaires or the customer's records is exposed. The session is bound to one questionnaire id.
15. TrustCenterPage is only partially modelled. The "page" is computed from other modules (answers, vendors, controls, resources) plus `trust-settings.publicPage {on, name, ref}`. There is no stored page content, branding or sections. Change history and activity are append-only kinds without retention. The update outbox lives in kv.
16. AccessRequest has two meanings in this group: workforce access requests (E-RK-15, internal systems) and Trust Center document access requests (E-RK-38, external). They should be separate tables. Access "systems" are free text, with no System or Application entity, and privileged status is inferred by regex on the system name.
17. The People module has no Person table. The workforce is computed from directory members plus contractors, and department is always "—" for members. Offboarding writes into other groups' records (controls, policies, delegations) and the directory (membership) in one transaction.
18. The AI register stores the FRIA (fundamental-rights impact assessment) and the EU AI Act classification inside the system record. That is related to, but not the same as, a GDPR DPIA. Bias tests keep only the latest result, and signals are capped at 200.
19. Commitments are one free-text `detail` per contract. There is no Contract, Customer or clause entity, the analysis is a regex match against static standard terms, and only one incident can be active at a time. Incidents are not linked to Issues, Findings, Notifications to customers or the breach-notice obligation of RoPA/DPIA (other groups).
