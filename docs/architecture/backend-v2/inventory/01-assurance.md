# Front-end inventory 01: Assurance and work (GROUPCODE AS)

Scope: features `overview`, `work`, `reports`, `frameworks`, `controls`, `evidence`, `policies`, `audits`, `issues` (`front-end/src/features/<name>/`), plus the external auditor's view of audits, evidence, controls, policies and frameworks. Paths are relative to `front-end/src/` unless they start with `docs/`. Read-only inventory: no source was changed. Field names and types only; no seed values.

Conventions used below:
- "Server today" names the route key as registered (`server/ws/routes.ts` merges each module's table; every key is served under `/api/`). All workspace routes go through `wsRoute` (`server/ws/common.ts`): the session's company member, role must open the module (`ROLE_MODS`, `data/roles.json`), deny by default.
- "ws_records:<kind>" means the generic JSON row table `ws_records (tenant_id, kind, id, data, version, created_ms, updated_ms, updated_by, deleted_ms)` with per-company counters in `ws_counters` (`server/ws/store.ts`). Four-eyes requests are the dedicated `approvals` and `approval_votes` tables; the company log is `audit_log` (hash chained); in-app notices go through `Store.insertNotice`.
- Roles are base roles; `admin2`/`owner2` behave as `admin`/`owner`. "Mgmt" = admin or owner.
- Who opens each module (ROLE_MODS): overview: admin, owner, analyst, auditor, employee. work: admin, owner, analyst, employee (tabs other than Tasks need module `me`: same roles; Delegation tab admin/owner only). reports: admin, owner. frameworks: admin, owner, auditor. controls: admin, owner, analyst, auditor. evidence: admin, owner, auditor. policies: admin, owner, auditor, employee. audits: admin, owner, auditor. issues: admin, owner, analyst.
- Demo mode (default build) runs every action on in-browser `DATA` (`lib/data.ts`, clone of `data/seed.json`) via `viaApi(mock, real)`; HTTP mode (`NEXT_PUBLIC_API_MODE=http`, `API_ON`) calls the server route listed.

### Gaps and observations

1. Screens with no server endpoint: audit Control testing tab (S-AS-36; `Audit.tests` is always empty on the server and has no write route); "Create Tasklane ticket" on a control (`POST ws/controls/:id/ticket` is called by `features/controls/services/controls.ts` but not registered; button disabled in production); My remarks (MeRemark) and the demo task kinds Training/Reply (browser only); Overview and Reports trend charts, "Issues closed" KPI and month-on-month deltas (no metric history stored); Account security tab (demo store only).
2. Server endpoints with no screen in this group: `GET ws/data/overview` figures are consumed implicitly; `POST ws/report-approvals/:id/:decision` is decided from the notifications bell, not from Reports; `evidence-tombstone` records are written but never listed; `GET ws/data/auditlog` and related routes live in `server/ws/audits.ts` but belong to the Audit Logs screen (other group); FrameworkState.audit ("Next audit") is read but never set.
3. Auditor scope is role based, not engagement based: an auditor reads every control, test, evidence item (and downloads every file), policy and framework of the tenant, regardless of assignment or access window; only the audits module enforces assignment and expiry. A redesign should scope Evidence, Control and Policy reads to the auditor's live engagement(s) and the engagement's frozen populations. The auditor can also acknowledge policies (no role gate).
4. Evidence has no relationships: no link to Control, Requirement, Framework, Audit, PBC request or Finding; no expiry, freshness or "valid until" date; a "version" is only a counter and note (files are not versioned with it). "Freeze populations" records a timestamp but locks nothing. The required entity Evidence (versions, expiry) is therefore only partially covered.
5. Two mapping stores: requirement side (`FrameworkState.reqCtrl`) and control side (`Control.map`). The server keeps them in step for catalogue requirements, but control-side refs that are not catalogue ids (free text) exist only on the control. A proper ControlMapping table (framework, requirement, control, source, by, at) is needed. No unmap route exists on the control side; there is no unlink for Issue links or Policy mapped controls either.
6. People are stored as both display name and user id inside JSON (owner/ownerId, by/byId, editors/editorIds, etc.). Display names are personal data duplicated into many records and into audit targets; a redesign should store user ids only and resolve names. PolicyAcknowledgement keeps one row per person and policy (latest version only); per-version acknowledgement history lives only in `audit_log`.
7. Personal or sensitive data: evidence files (screenshots, exports, records) can contain employee or customer personal data, possibly special-category; automated test items name employee accounts (collapsed for non-admins); report schedule recipients are email addresses; the server derives the company's email domains from members' emails; VendorRequest carries a "processes personal data" flag; free-text fields (IR items and responses, finding titles, RCA, evidence notes, policy bodies, exception reasons, delegation reasons) may hold personal data; audit_log stores actor name and IP.
8. Dates and identifiers: Audit has no structured start, end or fieldwork dates (`period` is free text such as "Planning" or "Access <date> to <date>"), so the Overview Focus card and Compliance calendar cannot date production audits. Audit.fw is a display string from a fixed list, not a framework id. AuditControlTest.ctrl is unchecked text. Policy.review is a formatted display date. Test.last is display text.
9. Demo-only behaviour: frameworks start in scope in the demo but out of scope on the server; demo seeds requirement mappings by hashing; demo acceptance figures are random; demo evidence attachments are fabricated names and sizes; demo test runs never execute; demo control ticket keys are random; demo auditors see audits by lead text; DataTable "Export selected" CSV is never audited in either mode.
10. Analyst inconsistency: evidence rules allow analysts to write and review, but ROLE_MODS gives analysts no evidence module, so the server refuses them at the route. Analysts can acknowledge published policies only through My Work.
11. AuditFinding status `Closed` exists but nothing sets it; findings are not closed when their Issue closes. Finding -> Issue is the only CorrectiveAction model (Issue with tasks, root cause, corrective text and verified closure).
12. Notifications are text only (no type, record link or read state stored by these routes).
13. Required entities coverage:
    - Covered: Framework (library + custom + per-tenant state), Requirement (reference rows), Control, Policy (versions, approvals, attestations via acknowledgements and owner attestation on controls), Audit, Finding, CorrectiveAction (as Issue), AuditLogEntry (written by every action), Notification (written; read elsewhere).
    - Partially covered: ControlMapping (two embedded maps, no table), Evidence (versions as counter only, no expiry), Membership/User/Role (read only: members picker, role gates from `data/roles.json`), Permission (static ROLE_MODS plus per-action role lists in `lib/rulesWs.ts`; no stored permissions), AccessRequest (created from My Work, owned by Access group), Vendor (VendorRequest only), Risk (read for links, posture and reports; RiskSnapshot shared with auditors), Assessment (audit engagement only; no control self-assessment entity).
    - Not covered by this group: Tenant, Asset, Threat, Vulnerability, RiskTreatment (only treatment actions read in My Work), Questionnaire, TrustCenterPage, ProcessingActivity (RoPA), DPIA, DataSubjectRequest, Plan, Subscription, Invoice.
