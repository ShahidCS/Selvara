# Phase 1 front-end inventory, group 03

Documentation only. Field names and types come from the code. No values are copied from seed data. "Mock" is the default demonstration build (`NEXT_PUBLIC_API_MODE` unset, in-browser synthetic data). "Prod" is `NEXT_PUBLIC_API_MODE=http` against `front-end/src/server`. Several modules render a different component in each mode, so each mode gets its own screen row where the two differ.

Paths are relative to `front-end/src/` unless they start with `supabase/` or `docs/`.

## Company settings, audit log, privacy and AI

### Gaps and observations

1. **RoPA register is static reference content, not tenant data.** `RopaRegister.tsx` renders `data/platform.json` `ROPA`: 17 fixed activities (PA-01..PA-17), each with id, scope, name, purpose, lawful basis, data subjects, data categories, recipients, transfers, retention and Art. 32 measures (all free text). It is the same for every company. There is no table, no create/edit/delete, no owner, no version, no review date and no approval. The only server touch is an audit entry on export (`POST ws/exports`). The prod intro says "a reference register to adapt to your company", but nothing in the UI lets a company adapt it. ProcessingActivity therefore needs a new tenant entity (seeded from this template) with versioning and an owner.
2. **The RoPA link on each audit-log row is a client-side regex heuristic** (`lib/ropa.ts ropaFor`) over action, category and categories. The server does not store a processing-activity id per entry. `audit_log.basis` exists but the workspace screen does not show it.
3. **DPIA: only partial, and outside this group.** A general DPIA screen or entity does not exist. The only one is the per-AI-system "impact assessment (FRIA / DPIA)" in the `ai` feature (`features/ai/services/ai.ts saveFria`, `AiDetail.tsx`; server `POST ws/ai/systems/:id/impact-assessment[/submit|/approve|/return]`): status + summary with submitter ≠ approver. Retention, Team and Audit log have none.
4. **DataSubjectRequest (DSAR): absent everywhere.** No screen, service, server route or table exists. RoPA PA-13 "Data subject rights handling" describes the activity, but nothing implements intake, identity verification, deadlines, erasure or export. Integrations, help questions, join requests and the audit log all hold personal data a DSAR would need to find.
5. **Mock-only Team settings with no server endpoint**: review cycle, risk appetite, SLAs (`POST /team/settings` with these keys is ignored or refused: the server reads only `lockout`), workspace brand, procurement approvers (`/team/approvers`), "save settings" (`/team/settings/save`), trusted office networks (`/team/trusted-networks`; the server reads a **global** kv `settings/trusted` that no route writes), password minLength. Prod hides all of these tabs.
6. **Automation rules and data retention / legal holds are browser-only** (`governance.ts`). They have three four-eyes kinds (`team-rule`, `team-retention`, `team-hold`) that the server does not know. No purge or rule job exists. Retention floors are drafts for compliance review (FATF R.11 reference).
7. **Mock-only endpoints with no server**: `/integrations/:name/toggle|sync`, `/integrations/sync-all` (old mock paths; prod uses `ws/integrations/*`), `/billing/plan`, `/billing/payment-method`. The mock payment form collects card brand, last 4 digits, expiry and cardholder name. Prod removed the form on purpose.
8. **Server endpoints with no screen in this group**: `GET ws/members` (pickers), `POST v1/events` and `GET v1/:collection` (external API), `POST ws/assistant/prefill` (used by `components/kit/PrefillBanner.tsx` in other modules' forms), `POST billing/stripe/webhook`, `POST ws/delegations*` (screen is in `work`), the `admin/help*` and `admin/support*` staff side (Admin Console group).
9. **Role mismatch**: the Assistant service and SOD text allow `owner` to manage agents and decide runs, but ROLE_MODS denies owner the `assistant` module, and prod Team, API, Integrations, Billing and Audit log are admin-only. The redesign must pick one source of truth for module access versus action permission.
10. **Two four-eyes stores**: team kinds go through `server/directory.ts` (TEAM_KINDS) and workspace kinds through `server/ws/foureyes.ts`. Both live in `approvals`. Kinds seen in this group: team-role, team-invite, team-network\*, team-rule\*, team-retention\*, team-hold\*, integration.connect, api.key, api.webhook, ai.enable, ai.mask, assistant.agent.enable, assistant.agent.autonomy, assistant.agent.recertify, assistant.mcp.grant (\* = mock only).
11. **Personal data held in this group**: profiles/memberships/invitations/join requests (name, email); sessions and sign-in records (IP, device); audit_log (actor, IP, free-text targets that can contain names, emails and reasons); integration accounts (up to 5,000 per connection: name, email, MFA status, admin flag, last login: employee data from third-party identity providers); billing account contact and address; help questions (free text, though the screen warns against personal data); support grant reasons. No special-category data is collected on purpose. The free-text fields (help body, reasons, AI questions) could hold it. The PII blocker (`lib/pii.ts`) detects national ids, passport numbers, dates of birth, IBANs, cards and phone numbers before AI calls only.
12. **AI content is not retained**: questions and answers are not stored, only draft metadata (`ai-draft`) and audit entries. The mock thread is in memory. Agent run `draft` text **is** stored (`agent-run`).
13. **Audit log hashing differs by mode**: mock FNV-1a 32-bit (labelled not cryptographic), prod SHA-256 per tenant chain in the DB. The prod UI shows the newest 500 entries. Evidence packages store only metadata (id, by, entries, sha), not the file. Mock packages embed the RoPA. Prod packages do not.
14. **Billing data is platform-owned** (`platform_records`, kinds billing-account, billing-invoice, billing-entry, billing-checkout, billing-plan-request, billing-plan-answer). The company reads only its own rows. The mock Subscription/Plan shape (screenings, idv, storageGB limits; seats) differs from the prod PriceList (monthly, seats). Seat usage = count of active members.
15. **Notifications**: only `notices` (user_id, at_ms, text). It is used for security alerts, agent-run notices to record owners and integration sync failures. There is no read/unread state in prod, no type, no link and no preference table in this group (`lib/notifPrefs.ts` belongs to another group).
16. **Help articles** are static code (`data/helpArticles.ts`), not CMS data.
17. **Things I could not determine**: the exact `me/security` server query (sessions/notices limit), whether `team/members` exposes Suspended members' emails to all admins (it filters only Removed), and how `ws_records` kind names map to RLS beyond `tenant_id`. I did not inspect every line of `server/directory.ts`.

**Coverage of the required entity list (this group):**
- Covers: User (profiles, sessions, MFA, passkeys, recovery codes), Membership, Role (static RBAC + membership role), Invitation/join (AccessRequest-like for workspace membership), AuditLogEntry, Invoice, Subscription (BillingAccount + plan requests), Plan (PriceList), Notification (notices, minimal).
- Partially covers: Tenant (tenant_settings lockout only; the governance settings are mock-only), Permission (static ROLE_MODS, no per-tenant permission table), ProcessingActivity/RoPA (static template, read-only), DPIA (only the AI-system impact assessment, other group), Evidence (audit evidence packages only; control evidence is another group), Control (integration checks link to controls), AccessRequest (join requests and support grants; the access-module requests are another group).
- Lacks: DataSubjectRequest (none anywhere), a general DPIA, Framework, Requirement, ControlMapping, Policy, Asset, Threat, Vulnerability, Risk, RiskTreatment, Vendor, Questionnaire, Assessment, Audit, Finding, CorrectiveAction, TrustCenterPage (all in other groups or absent).
