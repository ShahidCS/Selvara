# Phase 4 independent audit: AppSec and access (auditor AUD2)

Finding ID prefix: P4-A2-. Checklist items covered: 6, 9, 10, 12, 13, 17, 18.

## 1. Summary

I audited the Selvara back-end v2 design in `docs/architecture/backend-v2/` (read-only). Scope: phase2 `2C-api.md` (endpoint catalogue §1 to §6), `2E-iam.md` (E-30 permission catalogue, E-31 RBAC matrix, E-33 to E-46, E-55 to E-80), `2F-security.md` (F-1 to F-15, including every row of F-2 and F-3 and the F-2.13 acceptance register), `2H-infrastructure.md` H-6, `2J-testing.md` (J-AUTHZ, J-SEC, J-ISO), `2D-workflows.md` (D-03c, D-06, D-79), `2B-data-model.md` (B-E23.1, B-E09.7, B-E90.37), `2G-privacy.md` (retention), ADR-009, ADR-012 and ADR-013, the registers (`risks.md`, `open-questions.md` OQ-05 to OQ-25, `decisions-log.md`, `assumptions-log.md`) and the Phase 3 review P3-X2. Overall, the access design is strong and mostly testable. It has deny-by-default `can()` with object rules in the repository layer (E-35), auditor and vendor scopes enforced by restrictive RLS (F-ISO-12, F-ISO-14), and authorisation tests generated from a machine-readable endpoint registry (J-AUTHZ-01 to -04). Upload scanning is fail-closed and served from a cookieless origin. Audit anchoring is external, signed and time-stamped. The CI pipeline has SAST, SCA and secret scanning, plus orchestrated migrations. My opinion is **qualified**. The OWASP ASVS gap list exists only at chapter level and is not a requirement-level L2 gap list. Audit-log coverage leaves out several sensitive reads and every refused read. Member-vendor access is not time-boxed. The production gate may still be self-approved. The threat-acceptance registers contradict the owner's recorded decision. Only item 13 passes outright.

## 4. Positive observations

- Object rules are enforced in the repository layer, not in handlers (E-35). Authorisation tests are generated from a machine-readable endpoint registry and role matrix. The build fails on an endpoint with no declared permission, and weekly mutation testing proves the suite catches changes (J-AUTHZ-01 to -05).
- Auditor scope is defence-in-depth. The auditor path has OBJ-AUD in the API, the `_ro` role with restrictive RLS keyed on `app.engagement_id`, a per-request window check, 404 instead of 403, no member ids, and a logged view (F-AB-08, F-ISO-12, J-AUTHZ-20/21).
- Tamper evidence is a strong design: per-chain hashes over keyed HMACs (survives erasure), hourly Merkle anchors signed in KMS, RFC 3161 time stamps, compliance-mode WORM in a separate account, and offline tenant verification bundles (ADR-013).
- The upload pipeline is fail-closed. The scanner signs its verdict and the verdict is bound to the file hash. Downloads use a cookieless origin with `CSP: sandbox` and single-use, purpose-bound tokens (F-10, ADR-012).
- R-56 is documented honestly. The design states that the escape succeeds, and the tests prove the prevention and detection controls instead of asserting a false negative (F-ISO-06, F-IT-11).
- Support access needs a customer grant, is time-boxed (≤8 h grant, ≤60 min session), read-only, limited to the granted parts and excludes files and DSAR data. Each view is logged in both logs (E-75 to E-75b).
- Migration orchestration has canaries, health-gated batches, a version window, drift detection and fail-closed `Maintenance` (ADR-009, H-6.3).
