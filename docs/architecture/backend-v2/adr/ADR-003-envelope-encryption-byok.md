# ADR-003: Envelope encryption, crypto-shredding and BYOK through a key-provider abstraction

| | |

| Date | 2026-11-23; revised 2026-11-24 (rev P4: KS-SNAP, ISO-HARD, PITR on `ks`; rev P5: KS-SNAP keep-newest rule RA-01, deputy approver R-DEP in the `ks` restore) |

| Related | ADR-001 (C1-02, C1-08), ADR-002 (decision 9, ISO-HARD), ADR-004 (backups), ADR-010 (control plane), ADR-013 (WORM), spine S7, `2F-security.md` F-7 (F-7.5 KS-SNAP), F-4.5 (ISO-HARD), `2G-privacy.md` G-6; P4-A1-07, P4-A1-01, P4-A1-04 (rev P4) |

## Context

- Supabase encrypts each project at rest with one provider-managed key. There is no per-tenant database key (ADR-001 C1-02).
- The owner needs BYOK (Q-16), lifetime backups of every change (Q-24), and deletion that is evidenced (Q-24). Crypto-shredding is accepted subject to the conditions in discovery §6 (OQ-03).
- Spine S7 requires: a per-tenant KEK in an external KMS outside the database and its backups; a per-tenant DEK; per-subject keys in a separate store with short backups; four-eyes and a certificate for key destruction.
- Supabase Vault stores secrets inside the database, so its contents travel with database backups. pgsodium is pending deprecation. Neither can hold a key that must not be in the data's backups.
- Health-sector customers may store special-category data (A-14).

## Options considered

| Option | Description | Pros | Cons |
|---|---|---|---|
| O1 Provider encryption only | Rely on Supabase at-rest encryption | No work; no latency | No per-tenant keys, no BYOK, no shredding; fails Q-16, Q-24, C1-08 |
| O2 Per-tenant KEK in external KMS, DEK in the database (Vault) | Envelope encryption with wrapped DEK kept in Vault | Simple; one external call per DEK unwrap | Tenant-level shredding works (KEK destruction), but per-subject keys in Vault sit in long backups, so subject erasure cannot reach backups |
| **O3 Per-tenant KEK in external KMS; wrapped DEKs, subject keys and file keys in a separate key store `ks` with short backups** | Three-level hierarchy; key-provider abstraction; BYOK by cross-account key | Meets S7 fully; tenant, subject and file shredding all reach backups within a known window; BYOK natural | One more database project; key-store availability becomes critical; field encryption limits search |
| O4 One KMS key per subject | Every subject key in the KMS | Strongest shredding evidence | Cost and KMS quota per key at scale; latency; impractical for thousands of subjects per tenant |
| O5 Database per tenant with separate encryption | Rejected by ADR-001 | Strong separation | Not available (ADR-001 fixed) |

## Decision

Adopt **O3**.

1. **Key-provider abstraction** (`KeyProvider`): `generateDataKey(ctx)`, `wrap(ctx, key)`, `unwrap(ctx, wrapped)`, `scheduleDestroy(keyRef, approvalId)`, `health(keyRef)`. Adapters: the KMS in `kms-prod` (H-AC-05, launch), customer KMS (BYOK, same provider family at launch), others later.
2. **Hierarchy** (F-K-01 to F-K-05): tenant KEK in KMS; tenant DEK (AES-256-GCM) wrapped by the KEK; subject keys, file keys and the blind-index key wrapped by the DEK. **Platform KEK** (F-K-30, `kek/platform` in `kms-prod`, with a multi-Region replica): wraps the platform DEK (F-K-31), which encrypts the E1 fields of the control plane `cp` (for example `control.identities.email`, looked up by an HMAC blind index under F-K-32), and the platform audit HMAC key. The platform KEK never protects tenant data and is not destroyed while the platform runs. (rev P3)
3. **Key store `ks`**: separate small Postgres project in `R1`; PITR **on with a 7-day window** (DU-02 recommendation, owner decision pending; rev P4, was off; rev P5); daily backups kept 7 days; reachable only by the `keysvc` module role `ks_rw`, which has no table grants and only `EXECUTE` on SECURITY DEFINER functions that take no tenant argument and read `app.tkey` set by the router (ISO-HARD b, 2F F-ISO-41, rev P4); tables `ks.tenant_dek`, `ks.subject_key`, `ks.file_key`, `ks.platform_dek` and the wrapped blind-index and audit HMAC keys. Holds wrapped material only. **Wrapped per-file and per-subject keys live only in `ks`, never in tenant tables; tenant tables hold only key ids and versions** (DA-04). (rev P3)
   - **Resilience (rev P3, DA-11):** a **standby in the DR region** (streaming replica, *verify Supabase cross-region replicas*) and an append-only **key journal** in `offsite-prod`: every `ks` insert and every delete (as a tombstone) is written as an object with wrapped material only, under compliance object lock, expiring **8 days** after it is written. Recovery: promote the standby, or restore by PITR or the last daily backup and replay the journal with its tombstones (RPO 5 min, RTO 4 h). `ks` is excluded from tenant exports, the `control` export, WORM audit segments and every other off-site copy except the key journal and KS-SNAP.
   - **KS-SNAP (rev P4, closes P4-A1-07; detail 2F F-7.5):** the standby, PITR and backups all sit in the Supabase organisation `prod`, so losing that organisation (or the region without a working standby) would have lost every key older than the 8-day journal. A job in `workloads-prod` (role `ks_snap_ro`, one export function, no access from `app` or `console`) writes a **daily logical snapshot** of `ks` (wrapped tenant and platform DEKs, subject keys, file keys, blind-index and audit HMAC keys, key metadata, and the journal high-water mark) to a dedicated WORM bucket in `offsite-prod`, a cloud account in a different provider organisation from Supabase. Each snapshot is under **compliance-mode object lock for exactly 8 days**. Key handling: each snapshot is encrypted with AES-256-GCM under a data key from a dedicated off-site KEK `kek/ks-snap` in that account's KMS (context `{purpose, snapshot_id, taken_at}`). The writer can only generate data keys, never decrypt. Decrypt is possible only through the `ks-restore` role, which needs two different people covering R-A and R-B with hardware keys (the deputy approver R-DEP may stand in for one of them, never both; rev P5) and a four-eyes approval. The manifest (counts, hashes, journal high-water mark) is signed with F-K-06. Recovery after loss of Supabase or the region: place the keep-newest hold (below), rebuild `ks` in a fresh project (another Supabase organisation, or a managed Postgres host in the DR region of `workloads-prod` if Supabase is unavailable *(verify, OD-14)*) from the latest snapshot, then replay the journal from the snapshot's high-water mark, tombstones applied. **Restore drill** quarterly and as a V2-R0 exit criterion: rebuild into a fresh project and decrypt a sample of E2 fields and files (V3-11). Vendor fallbacks (no compliance mode, lifecycle timing) are in 2F F-K-46.
   - **Keep-newest rule (rev P5, RA-01; detail 2F F-K-47, 2H H-KS-11):** when a `ks` loss or compromise is declared (S1 incident), the first step of the restore runbook places a legal hold in `offsite-prod` on the newest KS-SNAP object and on the key-journal objects written after it, until `ks` is restored and verified. The hold extends the existing lock and makes no new copy. It needs one approver (R-A, R-B or R-DEP), because it only preserves data, and is released by four-eyes after the restore verification passes. Without it, a rebuild that took longer than the 8-day lock would lose every key again (the P4-A1-07 failure). It applies only to objects written before the declared loss; the deletion certificate (2D D-12e) records any key destroyed in that window as "destroyed; unrecoverable once the hold is released", with the release timestamp.
   - **Deputy approver (rev P5, P4-A3-19; detail 2F F-K-48, 2H H-KS-12):** the contracted deputy approver R-DEP, appointed by the owner, may stand in for R-A or R-B (never both in the same action) in `ks.restore`, the `ks-restore` role and `ks.hold_release`, so the `ks` RTO does not depend on both principals being reachable. KS-SNAP does not protect against loss of the tenant KEKs; that depends on KMS multi-Region replicas (VC-14, ADR-004).
   - **Destruction window (rev P3, rev P4):** a destroyed key leaves the live store and the standby at once (the delete replicates), the PITR window within 7 days, the daily backups within 7 days plus the 1-day backup cycle, the journal when the object holding its insert expires (at most 8 days after the insert, so at most 8 days after destruction), and KS-SNAP when the last snapshot written before the destruction expires: its lock ends at most 8 days after the destruction and the deletion job removes it within 15 minutes, with lifecycle expiry as the backstop (2F F-K-44). No copy holds a destroyed key more than **8 days after destruction**, except under the keep-newest hold after a declared `ks` loss, which the certificate records (rev P5). Replay never restores it, because tombstones are applied after any snapshot restore.
4. **Encryption classes** E0, E1, E2 per column (F-D-12), the only codes used; narrative and description free text that may hold personal or confidential data is E1; titles, refs, enums, dates and scores stay E0 and searchable (DA-01); in `cp`, E1 uses the platform DEK (rev P3); E2 scope per 2G (G-D-02). Ciphertext carries key id and version; AAD binds tenant, table, column and row (files: object id, version, segment).
5. **Exports and history** keep ciphertext as stored; the export (including the off-site copies of ADR-004) escrows the tenant DEK wrapped by the KEK, which stays in `kms-prod`.
6. **Destruction**: tenant (offboarding), subject (erasure), file (deletion) per F-K-10 to F-K-12. Tenant destruction schedules deletion of the KEK and every multi-Region replica (rev P3). KEK destruction needs a four-eyes `control.platform_approvals` id; a KMS event without one raises an alert and is cancelled within the waiting period.
7. **BYOK**: customer KMS key referenced in `control.key_registry`; test wrap with context; tenant four-eyes; re-wrap of DEKs; hourly health; revocation sets `KeyUnavailable`.
8. **Rotation**: KEK yearly (KMS automatic); DEK yearly with background re-encryption; subject keys re-wrapped on DEK rotation; file keys never rotate; `kek/ks-snap` yearly (KMS automatic), never scheduled for deletion while `ks` exists (rev P4).
9. **Tenant binding of key use (ISO-HARD a and d, rev P4, P4-A1-01; detail 2F F-ISO-40, F-ISO-43):** `keysvc` calls KMS for `kek/<tkey>` only in a short-lived session requested by the router for the routed tenant, tagged with that `tkey`. Each tenant KEK's key policy requires the session tag and the encryption context `tkey` to equal the key's own tenant, so a DEK unwrapped for one tenant cannot be obtained or used for another. A detector joins KMS audit events with the router's request log and raises a Sev-1 (F-M-19) on any mismatch. *(verify session-tag conditions in the chosen KMS, A-48)*; fallback: per-tenant grants with an encryption-context constraint, used only by `keysvc`, as stated in F-4.5.

## Security and privacy implications

- Meets discovery §6 conditions 1 to 4: granularity (tenant, subject, file), every copy destroyed (KEK only in KMS, wrapped keys only in `ks`, its standby, its 7-day PITR and backups, its 8-day key journal and its 8-day KS-SNAP snapshots, so every copy is gone 8 days after destruction) (rev P3, rev P4), AES-256-GCM with no plaintext copies (F-K-R4), evidence (certificate, KMS logs, anchored audit entry).
- E0 plaintext (titles, states, ids) remains in Supabase backups until roll-off; disclosed in the DPA (G-6.2).
- A compromised `app` function can still decrypt any tenant's data through KMS by requesting a session for that tenant (C1-01 class risk, accepted and re-confirmed by the owner on 2026-11-24, OD-15). ISO-HARD (decision 9 and decision 3) bounds the injection and routing-bug cases: an escape inside one tenant's request cannot obtain another tenant's keys. Detection: KMS anomaly alerts (F-M-06) and the tenant-mismatch detector (F-M-19). (rev P4)
- KS-SNAP copies wrapped key material to a second provider organisation. Its contents are wrapped twice (by the tenant DEK and KEK inside, by `kek/ks-snap` outside), the writer cannot decrypt, and decryption needs two people covering R-A and R-B (R-DEP may stand in for one of them, rev P5). It extends the 8-day destruction bound only under the keep-newest hold after a declared `ks` loss, for objects written before that loss, and the certificate records it (rev P4, rev P5).
- Provider operators of Supabase see ciphertext for E1/E2 and files; keys sit with a different provider account.
